- **Cursor 官方额度恢复（重要）**：10 月底起 Cursor 卡片一直显示「配置异常 / Invalid response: Cursor refresh failed」，额度停在旧缓存。根因是 Cursor IDE 把 `cursorAuth/accessToken`、`cursorAuth/refreshToken` 改为 Electron safeStorage 加密存储（值为 `cursor-safe-storage:v1:` + base64 的 `v10` 密文，密钥在钥匙串项 `Cursor Safe Storage` / `Cursor Key`）。旧实现把这段密文直接当 token 使用：请求 `cursor.com/api/usage-summary` 得到 401，随后刷新把密文当 `refresh_token` 发给 Cursor，Cursor 返回 `200 {"access_token":"","shouldLogout":true}`，最终被归到 `invalidResponse`，界面于是误报成"配置错误"。本版新增 `CursorSafeStorage`：识别前缀 → base64 解码 → 用钥匙串密码走已有的 safeStorage 解密（AES-128-CBC / `v10`）→ 取出真实 JWT；旧版 Cursor 的明文 token 原样透传，且**不会**因此去读钥匙串。
- **错误分类修正**：Cursor 刷新返回 `shouldLogout` 或空 `access_token` 时改为 `unauthorizedDetail`，界面显示「认证故障 + 请在 Cursor IDE 中重新登录」，不再把"需要重新登录"报成"接口配置异常"。解密失败（例如钥匙串被拒）同样给出可操作提示，并且**在发出任何请求之前**失败，不会再拿密文去试探。
- **凭证安全**：加密存储的数据库不再被写回明文 token —— 否则 Cursor 自身会读不出自己的凭证。明文存储的旧版本仍保持原有的刷新回写行为，不受影响。
- 测试：新增 11 项（解密器 6 项：明文透传/密文解密/无密码/解密失败/JWT 提取/非 JWT 明文；provider 5 项：解密后 Cookie 携带真 token、解不开不联网、`shouldLogout` 映射、加密时不写回、明文仍写回），全量 1,494 项测试 0 失败。
- 本机验证：覆盖安装后连续三次抓取（含进程重启）均静默成功，取到实时额度（Cursor Models 剩余 85.18%、Other Models 100%，账期至 2026-11-12）；Cursor 自身 `state.vscdb` 未被修改（mtime 与 token 密文均保持原样）。

- 首次升级需要授权一次钥匙串：`Cursor Safe Storage` 的 ACL 只信任 `/Applications/Cursor.app`，其他程序只能由用户弹窗授权。授权后该项绑定 `/usr/bin/security` 的签名（稳定），覆盖安装不会重复询问；实测同一份构建重启应用 0 弹窗。

### English

- Cursor official quota is fixed (important): since late October the Cursor card was stuck on "Config Error / Invalid response: Cursor refresh failed" with stale numbers. Cursor IDE now stores `cursorAuth/accessToken` and `cursorAuth/refreshToken` encrypted with Electron safeStorage (`cursor-safe-storage:v1:` + base64 of a `v10` blob, key in the `Cursor Safe Storage` / `Cursor Key` keychain item). The old code sent that ciphertext as the session token: `cursor.com/api/usage-summary` answered 401, the refresh sent the ciphertext as `refresh_token`, Cursor replied `200 {"access_token":"","shouldLogout":true}`, and the failure was classified as `invalidResponse` — hence the misleading "config error". This release adds `CursorSafeStorage`: strip the prefix, base64-decode, decrypt with the keychain passphrase through the existing safeStorage crypto (AES-128-CBC / `v10`), and extract the real JWT. Plaintext tokens from older Cursor builds pass through unchanged and never read the keychain.
- Refresh classification fix: `shouldLogout` or an empty `access_token` now maps to `unauthorizedDetail`, so the card shows an auth error with a "sign in again in Cursor" hint instead of a configuration error. Undecryptable credentials fail with an actionable message before any request is sent, instead of probing the API with ciphertext.
- Credential safety: an encrypted `state.vscdb` is never written a plaintext token back, which would leave Cursor unable to read its own credential. Plaintext stores keep their previous write-back behavior.
- Tests: 11 new (6 decryptor: plaintext pass-through, decryption, missing passphrase, decryption failure, JWT extraction, non-JWT plaintext; 5 provider: decrypted token in the Cookie header, no network when decryption fails, `shouldLogout` mapping, no write-back when encrypted, write-back still happens for plaintext). Full suite: 1,494 tests, 0 failures.
- Verified on a real machine: three consecutive fetches after overwrite install (including a process restart) all succeeded silently with live data (Cursor Models 85.18% remaining, Other Models 100%, cycle ends 2026-11-12); Cursor's own `state.vscdb` was not modified.

### Verification and limits

- The first upgrade needs one keychain approval: the `Cursor Safe Storage` ACL only trusts `/Applications/Cursor.app`, so other apps must ask the user once. After approval the grant is bound to `/usr/bin/security` (stable), so overwrite installs do not ask again; restarting the same build produced zero prompts.
- Known limit: the decrypted Cursor session token expires on 2026-12-24. If the Cursor IDE is not used in the meantime it cannot renew itself, and the card will ask you to sign in again in Cursor; normal Cursor usage writes a fresh encrypted token back, which this app decrypts on the next read.
- The local build is ad-hoc signed and not notarized; official signing, notarization, and installers come from the GitHub Release pipeline.
